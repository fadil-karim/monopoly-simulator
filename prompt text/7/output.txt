Three things in this release, v1.6 on main, and then your two questions.

Why the page looked broken, and the fix. Your screenshots show the new page under an old stylesheet. The first two releases told browsers to keep everything under /assets/ for a year without asking again, so your browser kept the very first stylesheet (system fonts, no red plate, the editions as a bulleted list) and laid it over every newer page. A later caching rule cannot reach an entry a browser has already stored, so the scripts and the stylesheet now live at new paths, which every browser fetches fresh, and from now on they are checked on every load, so it cannot happen again. After this deploy a normal reload is enough.

The board edition is now a plain dropdown in the header, "Board: London · £", nothing else.

Perplexity. There is a new provider for Perplexity's Agent API, which speaks the OpenAI Responses shape and serves other companies' models under provider-prefixed ids with one key. The example config now sends ChatGPT, Grok, Kimi and GLM through it as openai/gpt-5.5, xai/grok-4.7, perplexity/kimi-k3 and zai/glm-5.2, with your effort setting mapped to Perplexity's preset and no web search requested, so a call costs only its tokens. Claude and Gemini stay direct as you asked. Mimo and Mistral stay on their own keys because Perplexity's catalogue, as far as I could verify from here, does not serve them; moving one later is two fields in the config. One caution: those four ids come from Perplexity's changelog and integration pages rather than the live catalogue, which I could not reach from this machine, so before the first real game run `node runner/run.mjs --list-models perplexity` with your key and correct any id that is not listed. A wrong id would make that seat fall back to the rule-based bot on every decision, and the model-calls feed would show the error.

Where the live data is stored. In Cloudflare D1, a SQLite database bound to the site's Worker. The runner posts every event and model call to the site within a second of it happening, the Worker writes them to D1, and every viewer reads from D1 through the API, live or years later. The machine that plays the games also keeps a JSON copy of each game in runner/out. Nothing lives in anyone's browser except the chosen board edition.

How the backend runs. There is nothing to start: the API is the Worker, and Cloudflare builds and deploys it every time main is pushed, which it already does. What is missing is the database, which only you can create, once, from a terminal where wrangler is logged in (`npx wrangler login`): run `npx wrangler d1 create monopoly-ai`, paste the id it prints into the commented block in wrangler.jsonc, uncomment it and push; run `npm run migrate` to put the schema in; and run `npx wrangler secret put RUNNER_TOKEN` with a long random string of your choosing. From then on the site says "no game yet" instead of "no database yet".

How the simulation runs. On any machine with Node 20 or later and your keys: your laptop, a small VPS, anything that stays on. `npm install`, copy runner/config.example.json to runner/config.json, write runner/.env with SITE, RUNNER_TOKEN, ANTHROPIC_API_KEY, GEMINI_API_KEY, PERPLEXITY_API_KEY, XIAOMI_API_KEY and MISTRAL_API_KEY, then `node runner/run.mjs --loop`. It plays a game, uploads it as it goes, pauses a minute, and starts the next; Ctrl-C finishes the uploads and marks a running game aborted. `node runner/run.mjs --dry --games 1` plays one game without the site, to check the keys. On a server, `nohup node runner/run.mjs --loop &` or a systemd unit keeps it going.

Verified before the push: the provider adapters against a mock server, including the retry without the preset and the catalogue listing; the viewer suite through every tab with the dropdown; the engine and replay checks; the dry-run deploy; and the rendered pages.
